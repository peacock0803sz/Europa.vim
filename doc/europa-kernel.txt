==============================================================================
KERNEL CONNECTION					*europa-kernel*

Phase 3.2 adds the ability to start and interact with a Jupyter kernel
directly from Vim / Neovim.  A Jupyter Server subprocess is managed
automatically, or Europa can connect to an existing server.

The three entry-point commands are |:EuropaStartKernel|,
|:EuropaShutdownKernel|, and |:EuropaKernelStatus|.  They are documented in
|europa-commands|; this chapter explains the underlying mechanics.

KERNEL LIFECYCLE					*europa-kernel-lifecycle*

`:EuropaStartKernel` follows this sequence:

  1. Resolve the Jupyter executable (|europa-kernel-detection|).
  2. Acquire a server handle from the server pool (|europa-kernel-server-share|).
     - Subprocess mode: spawn `jupyter server` wrapped by the watchdog.
     - Attach mode: reuse the URL in |g:europa_jupyter_url|.
  3. POST `/api/sessions` to create a kernel session.
  4. Open a WebSocket to `/api/kernels/{id}/channels` with subprotocol
     negotiation (|europa-kernel-subprotocol|).
  5. Exchange `kernel_info_request` / `kernel_info_reply` to confirm the
     kernel is ready.  The reply populates the language and banner fields
     visible in |:EuropaKernelStatus|.

Once started, the kernel is stored in the buffer's `kernelRuntime` slot.
Shutting down (`:EuropaShutdownKernel`, `:bwipeout`, or `VimLeavePre`)
follows the reverse order: abort pending ops → WebSocket close(1000) →
DELETE `/api/sessions` → release server pool handle.

SERVER SHARING (Q1)					*europa-kernel-server-share*

A single `jupyter server` process can host multiple kernels.  Europa
exploits this by keeping one server per working directory (or per remote
URL): the first buffer that calls `:EuropaStartKernel` spawns the server;
subsequent buffers with the same key reuse it, incrementing a reference
count.  The server is terminated only when the last reference is released.

This means two `.ipynb` buffers in the same project share one server PID
but each get their own `kernel_id`.  `:EuropaKernelStatus` shows both the
shared PID and the per-buffer kernel ID.

ABORT AND RECONNECT (Q2, Q3)				*europa-kernel-reconnect*

Every pending asynchronous operation (WebSocket open, `kernel_info_reply`
wait, reconnect backoff sleep) is associated with the buffer's
`AbortController`.  A single `abort()` call — fired by `:EuropaShutdownKernel`
or by `:bwipeout` — cancels all outstanding work within 100 ms (SC-010a).

When the WebSocket closes unexpectedly, Europa enters a reconnection loop
using exponential backoff.  Three Vim variables control the policy:

  |g:europa_ws_reconnect_max_retries|
  |g:europa_ws_reconnect_initial_interval_ms|
  |g:europa_ws_reconnect_multiplier|

See |europa-configuration| for the valid ranges and defaults.

PYTHON ENVIRONMENT DETECTION (DESIGN.md §6.5)		*europa-kernel-detection*

Europa tries the following sources in order to locate the `jupyter`
executable:

  1. |g:europa_jupyter_executable| (explicit override).
  2. `.venv/bin/jupyter` in the current working directory.
  3. `venv/bin/jupyter` in the current working directory.
  4. `$VIRTUAL_ENV/bin/jupyter`.
  5. `$CONDA_PREFIX/bin/jupyter`.
  6. `jupyter` resolved from `$PATH`.

Set `g:europa_python_env_detect = 'disabled'` to skip steps 2–5 and use
only the explicit override or `$PATH`.  On Windows the `bin` sub-directory
is replaced by `Scripts` and the executable name is `jupyter.exe`.

SUBPROTOCOL NEGOTIATION (DESIGN.md §6.2)		*europa-kernel-subprotocol*

Europa follows the JupyterLab three-stage fallback when connecting the
WebSocket:

  1. `v1.kernel.websocket.jupyter.org`  (binary Jupyter wire protocol v1)
  2. `v1.token.websocket.jupyter.org`
  3. `v1.token.websocket.jupyter.org.{TOKEN}`  (token in subprotocol)

The token is also appended as `?token=...` in the WebSocket URL so that
servers which do not parse the subprotocol still accept the connection.

Use |g:europa_jupyter_ws_subprotocol| to force a specific protocol:
  - `'auto'`    — try the three-stage fallback (default)
  - `'v1'`      — force binary v1 subprotocol only
  - `'default'` — force the text JSON single-frame format

ORPHAN PREVENTION (Q4, SC-005a)				*europa-kernel-watchdog*

When Europa spawns `jupyter server`, it wraps it in a watchdog Deno script.
The watchdog polls the parent process PID every second.  If Vim is killed
with SIGKILL (or otherwise exits abnormally without running `VimLeavePre`),
the watchdog detects the parent's disappearance and sends SIGTERM to the
Jupyter server, followed by SIGKILL after 5 seconds.  The entire cleanup
completes within 15 seconds of the parent death (SC-005a).

EXTERNAL SERVER (ATTACH) MODE				*europa-kernel-external*

Set `g:europa_use_subprocess = v:false` to skip the subprocess spawn and
connect to an existing Jupyter Server:

  1. Set |g:europa_jupyter_url| to the server's base URL.
  2. Set |g:europa_jupyter_token| (or export `$JUPYTER_TOKEN`).
  3. Run `:EuropaStartKernel {name}`.

In this mode `:EuropaShutdownKernel` sends only the session DELETE request;
the external server process is left running.

CONFORMANCE TESTING (Q5)				*europa-kernel-conformance*

`tests/conformance/` contains end-to-end tests that run against a real
`jupyter server` installation.  They are excluded from `deno task check`
(the fast main CI gate) and executed instead via `deno task test:conformance`
or the `.github/workflows/e2e.yml` matrix workflow.

Prerequisites: `pip install 'jupyter-server>=2.15,<3.0' 'ipykernel>=7.0,<8.0'`

If `jupyter` is not in `$PATH`, the suite exits with a clear error message.

CELL EXECUTION (PHASE 3.3)				*europa-kernel-execute*

`:EuropaRunCell` sends a single `execute_request` over the WebSocket and
collects all iopub messages (`status`, `execute_input`, `stream`, `display_data`,
`execute_result`, `error`) until `execute_reply` is received.

The cell source is snapshotted at call time — edits during execution do not
affect the in-flight request (Q-edit). Each call generates a unique Jupyter
`msg_id` shared between the `execute_request` and the `pendingRequests` entry
(FR-003 shared UUID, SC-007 exactly-one-request gate).

Stream outputs from the same channel (`stdout` or `stderr`) that arrive
consecutively are concatenated into a single entry (per-message late-merge,
R03). The sign column shows `*` (busy), `…` (queued), or `!` (aborted).

Wire-level message flow: see `contracts/execute-message-flow.md` and
DESIGN.md §8.4 for the full sequence diagram.

INTERRUPT (PHASE 3.3)					*europa-kernel-interrupt*

`:EuropaInterrupt` sends `REST POST /api/kernels/{id}/interrupt` with the
current auth token. The kernel raises `KeyboardInterrupt` in the running
cell; the traceback is appended to the cell outputs.

When called while the kernel is idle the REST call still succeeds (the server
returns 204) and an informational message is printed. When called during a
reconnect cycle the REST request is skipped and the reconnect is aborted
instead (FR-011).

The token is sent both in the `Authorization` header and as `?token=` in the
request URL for broad server compatibility.

RESTART (PHASE 3.3)					*europa-kernel-restart*

`:EuropaRestartKernel` follows this sequence (FR-012):

  1. `AbortController.abort()` to cancel any in-progress execute.
  2. REST `POST /api/kernels/{id}/restart` (30 s timeout).
  3. On 200: close the old WebSocket (code 1000), open a new one.
  4. Exchange `kernel_info_request` / `kernel_info_reply` (re-handshake).
  5. Reset all cell `execution_count` to `null` and clear `cellStates`.

On REST failure (5xx, FR-013) the old WebSocket is left open so the kernel
remains usable without data loss. A "Kernel restart failed: …" message is
shown.

CANCEL QUEUED CELL (PHASE 3.3)				*europa-kernel-cancel*

`:EuropaCancelCell` drops the cell at the cursor from the pending-requests
queue without sending any network message (Q-cancel). Only cells in the
`queued` state (enqueued by `:EuropaRunAll` but not yet sent to the kernel)
can be cancelled. Cells in the `busy` state require |:EuropaInterrupt|.

REAL-TIME OUTPUT STREAMING (PHASE 3.4)		*europa-kernel-streaming*

During cell execution, iopub messages (`stream`, `display_data`,
`execute_result`) are buffered and flushed to the viewer every 16 ms via an
internal batch scheduler.  This reduces Vim RPC round-trips without
sacrificing responsiveness.  The 16 ms timer coalesces all queued messages
into one `denops#batch` call per tick (Q1=A / DESIGN.md §8.4); additional
immediate flushes are triggered on `execute_reply`, `status: idle`, and
structural cell operations.

When the viewer buffer is hidden (not visible in any window), the scheduler
skips the viewer RPC but continues accumulating outputs in memory so no data
is lost.  When the buffer becomes visible again — triggered by `BufWinEnter`
— a full re-render synchronises the display with the accumulated in-memory
state (Q-hidden-buffer).

Structural cell operations (|:EuropaInsertCell|, |:EuropaDeleteCell|,
|:EuropaMoveCell|, etc.) call an immediate flush at their entry point so that
any pending partial render completes before the line buffer is mutated.  This
prevents cell-marker offsets from drifting after the operation
(Q-structural-conflict).

COMM PROTOCOL TRANSPORT (PHASE 5.1)		*europa-kernel-comm*

Europa carries Jupyter's `comm_open` / `comm_msg` / `comm_close` traffic over
the same WebSocket the kernel uses for `execute_request`. Comm messages route
to a per-runtime CommService that maintains a registry of open comms and
dispatches inbound messages to handlers registered against a `target_name`.

Phase 5.1 ships transport-only. The library does not register any handler at
startup; built-in widget rendering (ipywidgets) is the responsibility of a
later phase. The `europa.test.echo` target is used by the test fixtures only.

Lifecycle rules:

  - On `:EuropaShutdownKernel`, `:EuropaRestartKernel`, and `:bwipeout` of a
    notebook buffer, every open comm receives a synthetic close event
    (origin `frontend-shutdown`, `frontend-restart`, or `frontend-wipeout`).
  - During a WebSocket reconnect, the CommRegistry is preserved unchanged so
    handler subscribers survive transient network blips.
  - `sendComm` raises a `KERNEL_RECONNECTING` error while the transport is
    mid-reconnect. Callers must retry after the runtime returns to
    `connected`; Europa never silently buffers comm traffic across a gap.

Binary buffers travel byte-for-byte through both wire codecs (v1 binary
offset-table and default text JSON); the Comm layer never base64-encodes or
JSON-stringifies a buffer mid-flight.

When multiple notebook buffers attach to the same kernel (only meaningful in
ZMQ-attach mode), each buffer holds its own CommRegistry and its own
target-handler Map. A kernel-initiated `comm_open` broadcast on iopub reaches
all attached frontends; their handlers (if registered) run independently and
keep distinct entries.

FUTURE SCOPE						*europa-kernel-future*

The following features are planned for later phases and are not yet available:

  - ZMQ connection mode for low-latency local kernels (Phase 4).
  - ipywidgets / `jupyter.widget` target handler and widget rendering
    (Phase 5 item 2).
